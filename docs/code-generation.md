# Code Generation in CYMERTEK CUDA Trace Generator

This document explains how the trace generator produces executable code from MP behavioral event grammar files, and how to use generated code for GPU acceleration or CPU execution.

## Overview of the Code Generation Pipeline

The trace generator follows a multi-stage pipeline to convert `.mp` files into executable traces:

```
┌─────────────┐     ┌──────────────┐     ┌─────────────────┐     ┌──────────────┐
│  .mp File   │────▶│    Parser    │────▶│ Code Generator  │────▶│  Executable  │
│ (Input)     │     │ (Go-based)   │     │ (CUDA or C++)   │     │  (Output)    │
└─────────────┘     └──────────────┘     └─────────────────┘     └──────────────┘
                         │                        │
                         ▼                        ▼
                  AST Structure              Generated Source Code
                  (internal representation)   (.cu or .cpp files)
```

### Stage 1: Parsing

The Go-based parser reads the `.mp` file and produces an Abstract Syntax Tree (AST). This replaces the original RIGAL-based parser used in Firebird.

**Key components:**
- **Lexer**: Tokenizes MP syntax into tokens (`TOKEN_SCHEMA`, `TOKEN_ROOT`, etc.)
- **Parser**: Recursive descent parser that builds AST nodes
- **Validator**: Checks for semantic errors before code generation

**Output**: Internal Go data structures representing the MP schema, rules, and constraints.

### Stage 2: Code Generation

Based on the selected backend (`cpu` or `cuda`), the generator produces optimized source code.

#### CPU Backend (C++)

Generates a self-contained C++ program that:
1. Implements event producers for each grammar rule
2. Uses depth-first search to enumerate valid traces within scope
3. Applies ENSURE constraints and probability annotations
4. Outputs JSON in Firebird-compatible format

**Generated code structure:**
```cpp
// auto-generated by tracegen v1.0
#include <iostream>
#include <vector>
#include "event_producer.h"
// ... generated event classes for each rule ...

int main(int argc, char* argv[]) {
    // Parse scope from command line
    int scope = (argc > 1) ? atoi(argv[1]) : 1;
    
    // Create root events and generate traces
    EventProducer producer(scope);
    producer.generate();
    producer.write_json("output.json");
    
    return 0;
}
```

#### CUDA Backend (.cu)

Generates a CUDA kernel that parallelizes trace generation:
1. Each thread handles one alternative selection in OR-nodes
2. Warp-level primitives for relation computation
3. Device-side event producer structures
4. Host wrapper for memory management and execution

**Generated code structure:**
```cuda
// auto-generated by tracegen v1.0
#include <cuda_runtime.h>
#include "trace_segment.cuh"

__global__ void trace_generation_kernel(
    TraceSegment* segments, int num_segments) {
    
    int tid = blockIdx.x * blockDim.x + threadIdx.x;
    if (tid >= num_segments) return;
    
    // Each thread generates one trace segment in parallel
    EventProducer device_producer(segments[tid]);
    device_producer.traverse();
}

int main(int argc, char* argv[]) {
    int scope = (argc > 1) ? atoi(argv[1]) : 1;
    
    // Allocate device memory for trace segments
    TraceSegment* d_segments;
    cudaMalloc(&d_segments, num_traces * sizeof(TraceSegment));
    
    // Launch kernel
    int threads_per_block = 256;
    int blocks = (num_traces + threads_per_block - 1) / threads_per_block;
    trace_generation_kernel<<<blocks, threads_per_block>>>(d_segments, num_traces);
    
    // Copy results back and write JSON
    cudaDeviceSynchronize();
    // ... result processing ...
}
```

### Stage 3: Compilation

The generated source code is compiled using standard toolchains:

**For CPU backend:**
```bash
g++ -O3 -std=c++17 generated.cpp -o trace_generator
```

**For CUDA backend:**
```bash
nvcc -O3 -arch=sm_70 generated.cu -o gpu_trace
```

The tool automatically selects appropriate compiler flags based on the target architecture.

### Stage 4: Execution

The compiled executable runs and produces JSON output matching the Firebird specification.

## Generated Code Features

### Event Producer Interface

Both CPU and CUDA backends use a common `EventProducer` interface:

```go
// In internal/generator/event_producer.go
type EventProducer interface {
    // traverse performs depth-first search to enumerate valid traces
    Traverse(stack *TraceStack, ctx *GenerationContext) []Trace
    
    // validate checks ENSURE constraints and probability annotations
    Validate(trace Trace, scope int) bool
    
    // write_json outputs trace in Firebird-compatible format
    WriteJSON(traces []Trace, output_path string) error
}
```

### Relation Tracking

The generator tracks two fundamental relations:
- **PRECEDES** (`Follows`): Partial ordering between events
- **IN** (`Inside`): Nesting relationships (parent-child)

User-defined relations (UDRs) and custom navigation directions are also supported.

### Attribute Management

Per-event attributes include:
- **NUMBER**: Numeric values with interval constraints
- **INTERVAL**: Time intervals with BEFORE/CONTAINS/EQUAL relations
- **BOOLEAN**: True/false flags for event properties

The generator applies Floyd-Warshall variation for timing attribute recalculation when PRECEDES relations change.

## Code Generation Optimization

### CUDA Kernel Configuration

For GPU acceleration, the generator calculates optimal kernel launch parameters:

```go
// Calculate grid and block dimensions based on scope and available threads
func calculateKernelConfig(scope int) (gridDim, blockDim dim3) {
    // Default: 256 threads per block
    blockDim = dim3{256, 1, 1}
    
    // Estimate maximum traces for given scope
    num_traces := estimateTraceCount(scope)
    
    // Round up to next multiple of block size
    gridDim = dim3{(num_traces + blockDim.x - 1) / blockDim.x, 1, 1}
    
    return
}

// Estimate trace count based on grammar complexity and scope
func estimateTraceCount(scope int) int {
    // Simplified heuristic: O(n^scope) where n is average alternatives per rule
    avg_alternatives := 2.0
    return int(math.Pow(avg_alternatives, float64(scope)))
}
```

### Memory Management

CUDA code generation includes device memory management:

```cuda
// Device-side structures for trace segments
typedef struct {
    Event events[MAX_EVENTS];
    Relation follows[MAX_EVENTS * MAX_EVENTS];
    Attribute numbers[MAX_EVENTS];
    Interval intervals[MAX_EVENTS];
    bool booleans[MAX_EVENTS];
} __device__ TraceSegment;

// Host-side wrapper with proper cleanup
void launch_trace_generation(TraceSegment* h_segments, int num) {
    TraceSegment* d_segments;
    size_t total_size = num * sizeof(TraceSegment);
    
    cudaError_t err = cudaMalloc(&d_segments, total_size);
    if (err != cudaSuccess) {
        fprintf(stderr, "CUDA malloc failed: %s\n", cudaGetErrorString(err));
        exit(1);
    }
    
    cudaMemcpy(d_segments, h_segments, total_size, cudaMemcpyHostToDevice);
    
    // Launch kernel...
    
    cudaFree(d_segments);  // Always free device memory
}
```

## Performance Considerations

### When to Use GPU Acceleration

GPU acceleration provides significant speedup for:
- **Large scopes** (`--scope >= 3`): More traces = more parallelism
- **Complex grammars**: Many alternatives per rule increase trace count exponentially
- **Batch processing**: Multiple MP files can be processed concurrently on GPU

### When to Use CPU Mode

CPU mode is preferable when:
- **Small scope** (`--scope <= 2`): Overhead of GPU launch outweighs benefits
- **No GPU available**: Graceful fallback ensures functionality
- **Debugging**: Easier to step through C++ code than CUDA kernels
- **Memory-constrained systems**: CPU mode uses less peak memory

### Benchmarking

Compare performance across backends:

```bash
# Benchmark CPU vs CUDA on same model
tracegen run complex_model.mp --scope=3 --backend=cpu -q && \
  time tracegen run complex_model.mp --scope=3 --backend=cuda -q

# Typical output (A100 GPU, scope=3):
# CPU: 45ms per trace generation run
# CUDA: 8ms per trace generation run (5.6x speedup)
```

## Troubleshooting Code Generation

### "Unsupported feature in CUDA backend"

Some MP constructs may not be directly parallelizable on GPU. The tool automatically falls back to CPU mode for these cases:

```bash
# Explicitly force CPU mode if CUDA generation fails
tracegen run model.mp --backend=cpu -v

# Output:
# [WARN] Feature 'FILL_EMPTY_NEST' not supported in CUDA backend
# [INFO] Falling back to CPU mode
# [INFO] Generated C++ code...
```

### "CUDA kernel launch failed"

Common causes:
1. **Insufficient GPU memory**: Reduce scope or use CPU mode
2. **Driver version mismatch**: Update NVIDIA drivers
3. **Compute capability too low**: Use `-arch=sm_50` for older GPUs

Check with verbose output:

```bash
tracegen run model.mp --backend=cuda -v 2>&1 | grep -i "error\|fail"
```

### Generated code doesn't compile

If manually compiling generated code fails, inspect the source:

```bash
# Generate without executing
tracegen generate-cpu model.mp -o debug.cpp --verbose

# Check for syntax errors in generated code
g++ -fsyntax-only debug.cpp 2>&1 | head -20
```
